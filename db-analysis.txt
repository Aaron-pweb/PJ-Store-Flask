 The current database architecture provides a solid foundation for a basic e-commerce application, but it requires several critical
  enhancements to be considered "commercial-ready," especially regarding financial integrity, auditability, and scalability.


  1. Financial Data Integrity
   * Current State: Monetary values (e.g., Product.price, Order.total_amount) are stored using db.Float.
   * The Issue: Floating-point numbers are unsuitable for financial calculations due to inherent rounding errors (e.g., 0.1 + 0.2 might
     result in 0.30000000000000004). In a commercial app, this leads to accounting discrepancies over time.
   * Recommendation: Convert all currency-related fields to db.Numeric(precision=10, scale=2). This ensures exact decimal arithmetic.


  2. Audit Trail & Payment Tracking
   * Current State: Payment references (tx_ref) are stored directly on the Order model. There is no separate record for payment
     attempts.
   * The Issue: If a user attempts to pay multiple times or uses different payment methods, you lose the history. It also makes it
     difficult to handle partial payments, refunds, or disputes.
   * Recommendation: Introduce a dedicated Payment model.
       * Fields: order_id, payment_gateway_ref, amount, status (Pending, Success, Failed, Refunded), raw_gateway_response, and
         timestamp.
       * This allows you to track every interaction with the payment provider independently of the order's lifecycle.


  3. Stock Management & Race Conditions
   * Current State: Stock is reduced after a successful payment is verified in the payment_success route or webhook.
   * The Issue:
       * Overselling: Two users could both pay for the last item simultaneously if they reach the payment gateway at the same time.
       * Inconsistency: If the webhook and the success_url both trigger, you must ensure the stock isn't deducted twice (idempotency).
   * Recommendation:
       * Implement a "Soft Lock" mechanism: When a user initiates checkout, reserve the items for a limited time (e.g., 15 minutes). If
         payment fails or the window expires, release the stock.
       * Centralize the "Mark Order as Paid" logic into a single service function to ensure it is handled identically and safely by
         both the UI redirect and the background webhook.


  4. Detailed Pricing Structure
   * Current State: Order.total_amount is a single snapshot.
   * The Issue: Commercial apps require a breakdown for legal and accounting purposes (Taxes, Shipping, Discounts).
   * Recommendation: Expand the Order model to include:
       * subtotal: Sum of items.
       * tax_amount: Calculated tax.
       * shipping_fee: Delivery cost.
       * discount_amount: Applied coupons or promos.
       * currency: To support future internationalization (e.g., "ETB", "USD").


  5. Data Redundancy & Snapshots
   * Current State: OrderItem stores price_at_purchase, which is excellent.
   * The Issue: OrderItem lacks a snapshot of the product name or variant details at the time of purchase. If a seller renames a
     product later, the user's historical order history will change.
   * Recommendation: Ensure OrderItem captures all relevant metadata (Product Name, Description, Variant Name) at the moment the order
     is placed.
